description: Optional evaluation of the user's voice pack. Use when the user asks "how good is my voice pack", "test it", "does it sound like me", or wants a blind test.

# Voice check

The CLI is `python3 -I ${CLAUDE_PLUGIN_ROOT}/scripts/wlm.py` (written `wlm`; one command per Bash call). This runs model calls through the user's own Claude Code login (`claude -p`, all tools disabled, from an empty temp dir, `ANTHROPIC_API_KEY` stripped): 3 per held-out message (brief, voice draft, plain draft) plus judge batches; `prepare` prints the exact estimate. Each voice draft sends the pack's budget of the user's real messages as a cached system prompt. Tell the user the estimate and get an OK before `generate`.

**Real data vs demo data.** A voice check is only meaningful on the user's own messages from their own voice pack. `prepare` prints `"data": "REAL: ..."` or `"data": "DEMO: ..."`, and the page shows the same label at the top (a yellow DEMO banner for synthetic data). Runs built from the plugin's synthetic test fixtures (`tests/fixtures/`, invented names like "Jordan Example") are always labelled DEMO. Never present a DEMO page or score as a test of the user's voice; if you build one (e.g. to show how the page works), say "this is a demo with made-up messages, not your writing" when you give it to them. Before a real test, run `wlm status` and confirm the pack is the user's (sources like teams / outlook / claude_code, not `synthetic`) and that it is a v2 pack with an archive (an old-format pack needs `wlm build` first).

**Important: don't contaminate the test.** You (this session) must not draft the test messages yourself or look at the held-out texts before the user takes the blind test; the scripted pipeline does the drafting in isolated calls. Don't print `items.jsonl`, `generations.jsonl` or anything under the run's `ctx/`.

1. **Prepare:** `wlm check prepare --register <reg> [--n 10] [--lineups 10]` (default chat; minimum 4 usable paired messages). It holds out `--n` real messages for the paired section and `--lineups` more for the lineup section (different messages, because a message seen in a pair would give away the fake in its lineup), typical length, replies first, spread over conversations, none within 48 hours of another in the same thread. It prints the run dir, the pair and lineup counts, whether the data is REAL or DEMO, a call estimate, and notes (e.g. too few other conversations to fill every lineup). Tell the user which it is.

2. **Generate** (after the user agrees): `wlm check generate [--run <dir>] [--model <id>] [--workers 4]`. For each held-out message: a content-only brief, then the write-as-me pipeline exactly as it ships (select the user's messages within the pack's default budget and strategy, with the held-out message, every other held-out message, their threads within 48 hours and near-duplicates excluded; the person file as the pack's default tier, minus every sentence that cites a held-out message (the run's `meta.json` counts them; a hand-written person file without citations can't be filtered, so use `--person none` for a clean test with one); assemble the context; one draft call; lint recorded) plus a "plain" Claude version with no voice pack as a baseline. `--budget`, `--strategy`, `--person core|full|none` and `--habits on|off` (the "How my messages vary" block, measured here on the archive minus the held-out messages) override the pack's defaults for the whole run, which is how to compare settings; the score report says which were used. Takes a few minutes.

3. **Blind test page:** `wlm check page [--run <dir>] --open` (add `--include-plain` to also pair the user's messages with the baseline: each held-out message then goes to one of the two conditions, so no real message is shown twice and each condition gets about half the pairs). It writes a self-contained `blind_test.html` in the run dir (local only; it contains real messages). Two parts: pairs, where they pick which message they really wrote, and lineups, where each shows four messages of similar length from the same register, three theirs from other conversations and one generated, and they pick the one they didn't write, with an optional note on why. Picks are kept in the browser and exported as JSON at the end. Tell them to answer before reading the review at the end, then export and give you the file path. If `page` reports lineup items left off (too few other messages of a similar length), say so.

4. **Score:** `wlm check score [--run <dir>] [--picks <exported.json>] [--judge-mode paired|lineup|both] [--no-judge]`. Picks are checked against the run's own answer key (`answers.json`, written by `page`); an export from a different run, or from an older version of the page (rebuilt since, e.g. with `--include-plain`), is refused. Reports:
   - the generation settings (strategy, budget, person file) and hard-rule breaks (how many voice drafts lint would have fixed)
   - stylometric distance (mean |z| over ~20 habits vs same-size samples of their own messages; lower is closer) for real held-out messages, the voice pipeline and plain Claude, and a 0-1 closeness score (0 = plain Claude, 1 = as close as their own held-out messages; clamped, with the raw value beside it, and "n/a" when plain Claude happens to be closer than the real messages)
   - median lengths
   - LLM judge, per condition, with 95% CIs: the **paired** fooling rate (forced choice, both orders; 50% = indistinguishable, 0% = always caught) and the **lineup** spotted rate (25% = chance, i.e. indistinguishable; 100% = always spotted). Each reason the judge gave for a catch is tagged **polish** (a typo, doubled word, apostrophe style, capitals, "too polished": things the plugin never fakes by design) or **voice** (everything else), and the voice-type catch rate is reported separately. Same-family judges are lenient-to-harsh in unknown ways; treat the numbers as relative, not absolute.
   - their own blind-test rates, paired and lineup, if picks were given, with the same polish/voice split of the notes they typed.

5. **Explain** in a few lines what the numbers mean. The lineup spotted rate is the headline: it is how a recipient meets a message (no real one beside it), and in the research the paired judge mostly caught real messages' typos, which a draft cannot and should not reproduce. If the voice-type reasons (in `judge.jsonl`) or the user's notes from the page point to a repeatable giveaway, offer to turn it into a hard rule, a learned note, a person-file claim or more archive messages via `/write-like-me:voice-learn` (with their OK). Typical findings: too long, too tidy, a detail the brief compressed away, or an opinion they wouldn't hold (the person file's job).

With 10 pairs and 10 lineups, confidence intervals are wide (about ±25 points); differences under ~20 points aren't meaningful. To compare two settings (e.g. budgets), run `generate` twice with `--run` on separate `prepare` runs, or score each with `--no-judge` first and judge only the one that looks better.
